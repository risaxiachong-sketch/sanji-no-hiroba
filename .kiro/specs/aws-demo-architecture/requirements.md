# 「さんじのひろば」AWS構成 要件定義書

## 背景と前提条件

本書は「さんじのひろば」コンテスト発表用デモのAWS構成を定義する。

| 項目 | 内容 |
|------|------|
| 目的 | コンテスト発表時にスマートフォンから実際に操作できるデモ環境を構築する |
| 開発体制 | AWS初心者2名 |
| 構成方針 | サーバーレス（サーバー管理不要）・従量課金（使った分だけ支払い） |
| 費用目標 | デモ期間中（1〜2週間）の月額 0〜5 USD以内 |
| 認証方式 | メールアドレスによるログインは行わない |
| データ保存 | プロフィール・「行ってみたい」→ LocalStorage（ブラウザ内保存）、投稿・リアクション・イベント → DynamoDB |
| ドメイン | 独自ドメインは取得しない（Amplify Hostingのデフォルトドメインを使用） |
| 施設側制限 | APIキーによる簡易アクセス制限（本格認証は不要） |

---

## 用語集

| 用語 | 説明 |
|------|------|
| Amplify Hosting | AWSのフロントエンド向けホスティングサービス。GitHubリポジトリと連携し、git pushで自動ビルド・デプロイ・HTTPS配信を行う |
| S3 | Amazon Simple Storage Service。ファイル保存サービス。イベント画像の保存先として使用 |
| API Gateway | HTTPリクエストを受け付けてLambdaに中継するサービス。「HTTP API」タイプを使用 |
| Lambda | イベント駆動で動くサーバーレス関数。呼ばれたときだけ実行される |
| DynamoDB | フルマネージドNoSQLデータベース。テーブル作成だけで使え、サーバー管理不要 |
| CORS | Cross-Origin Resource Sharing。異なるドメイン間でAPIを呼べるようにするブラウザの仕組み |
| LocalStorage | ブラウザにデータを保存する仕組み。サーバーに送信されず端末内に残る |
| ULID | 時刻順にソート可能なユニークID生成方式 |
| 署名付きURL | S3へのファイルアップロードを一時的に許可するURL。Lambda関数で生成し、フロントエンドが直接S3にアップロードする際に使用 |

## 1. 推奨するAWS全体構成

### 推奨構成図（テキスト表現）

```
スマートフォン
  ↓ HTTPS
Amplify Hosting（HTTPS配信・自動ビルド・デプロイ）
  └── 静的ファイル配信（HTML/JS/CSS）

APIリクエスト → API Gateway（HTTP API）→ Lambda → DynamoDB
                                            └→ S3バケット（イベント画像保存）
```

### 構成のポイント

- 全サービスがサーバーレス（サーバー管理不要）
- 全サービスが従量課金（リクエストがなければ課金なし）
- AWSの無料利用枠に収まる範囲で運用可能
- Amplify Hostingによりgit pushで自動ビルド・デプロイが可能
- HTTPS対応がAmplifyにより自動で行われる（証明書設定不要）
- Amplifyアプリを削除するだけでフロントエンド関連リソースを一括クリーンアップ可能

## 2. 使用するAWSサービスの一覧

| サービス名 | 種別 | 用途 |
|-----------|------|------|
| AWS Amplify Hosting | ホスティング | フロントエンドの自動ビルド・デプロイ・HTTPS配信 |
| Amazon API Gateway (HTTP API) | API管理 | フロントエンドからのリクエスト受付・Lambda呼び出し |
| AWS Lambda | コンピューティング | バックエンドロジック実行（TypeScript） |
| Amazon DynamoDB | データベース | 投稿・リアクション・イベントデータの保存 |
| Amazon S3 | ストレージ | イベント画像の保存（バケット名: `sanji-demo-images`） |
| Amazon CloudWatch Logs | 監視 | Lambda実行ログの保存（デバッグ用） |
| AWS IAM | アクセス管理 | サービス間のアクセス権限設定 |

## 3. 各AWSサービスの役割

### AWS Amplify Hosting（フロントエンド配信）
- GitHubリポジトリと接続し、git pushで自動ビルド・デプロイを行う
- React + Viteのビルドコマンドを自動実行し、静的ファイルをホスティングする
- HTTPS対応が自動で行われる（SSL証明書の発行・更新が不要）
- デフォルトドメイン（`*.amplifyapp.com`）を使用し、独自ドメインは不要
- Amplifyアプリを削除するだけでフロントエンド関連リソースを一括削除可能

### Amazon API Gateway（HTTP API）
- フロントエンドからのHTTPSリクエストを受け付ける
- URLパスに応じて対応するLambda関数を呼び出す
- CORS設定でAmplifyドメインからのリクエストのみ許可する
- 施設側APIにはAPIキーによるアクセス制限を適用する

### AWS Lambda（サーバーレス関数）
- TypeScriptで実装し、esbuildでバンドルしてデプロイする
- メモリ: 128〜256MB、タイムアウト: 10秒以内
- 投稿・リアクション・イベントの各CRUD操作を処理する
- 画像アップロード用の署名付きURLを生成する
- エラー時はCloudWatch Logsに記録し、適切なHTTPステータスを返す

### Amazon DynamoDB（NoSQLデータベース）
- オンデマンドキャパシティモード（読み書き発生時のみ課金）
- 無料利用枠: 25GBストレージ、月間25WCU/25RCU相当
- テーブル: 投稿テーブル、リアクションテーブル、イベントテーブル

### Amazon S3（イベント画像保存）
- イベント登録時にアップロードされた画像ファイル（JPEG/PNG）を保存する
- バケット名: `sanji-demo-images`
- パブリックアクセスをブロックし、署名付きURLまたはLambda経由でのみアクセス可能
- 画像取得時は署名付きURL（有効期限付き）でフロントエンドに配信する

## 4. スマートフォンから画面が表示されるまでの処理の流れ

① スマートフォンのブラウザでAmplify HostingのURL（`https://main.xxxxx.amplifyapp.com`）にアクセスする

② Amplify Hostingがリクエストを受け取り、ホスティングされた静的ファイル（HTML/JS/CSS）をHTTPSで返す

③ ブラウザがHTML/JS/CSSを読み込み、Reactアプリケーションが起動する

④ アプリがLocalStorageからプロフィール情報（ニックネーム・アバター）を読み込む

⑤ トップページが表示される

### 受け入れ条件
- スマートフォンのブラウザからHTTPSでアクセスできる
- Amplify Hostingのデフォルトドメイン（`*.amplifyapp.com`）で配信される
- git pushによりフロントエンドが自動でビルド・デプロイされる
- 初回アクセスから3秒以内にトップページが表示される

---

## 5. 投稿を登録・取得する処理の流れ

### 投稿登録

① ユーザーが投稿フォームにテキストを入力し、送信ボタンを押す

② フロントエンドがAPI Gateway（`POST /posts`）にリクエストを送信する

③ API GatewayがLambda関数を呼び出す

④ Lambda関数がULIDで一意のIDを生成し、ニックネーム・アバター・投稿日時と共にDynamoDBの投稿テーブルに保存する

⑤ Lambda関数が成功レスポンス（201）を返す

⑥ フロントエンドが投稿一覧を再取得して画面を更新する

### 投稿取得

① フロントエンドがAPI Gateway（`GET /posts`）にリクエストを送信する

② Lambda関数がDynamoDBから投稿を新しい順に取得する

③ 投稿一覧がJSON形式でフロントエンドに返却される

④ フロントエンドが投稿カード一覧を描画する

### 受け入れ条件
- 投稿にULIDが付与される
- 投稿にニックネーム・アバター・投稿日時が含まれる
- 投稿一覧は新しい順に返される
- 入力バリデーションで空投稿が拒否される

---

## 6. リアクションを登録・変更・取消する処理の流れ

### リアクション登録

① ユーザーが投稿に対して絵文字リアクションボタンを押す

② フロントエンドがAPI Gateway（`POST /reactions`）に投稿ID・絵文字種別・ユーザー識別情報を送信する

③ Lambda関数がDynamoDBのリアクションテーブルに保存する

④ フロントエンドがリアクション集計を再取得して表示を更新する

### リアクション変更

① ユーザーが既存リアクションとは異なる絵文字を選択する

② フロントエンドがAPI Gateway（`PUT /reactions/{id}`）に新しい絵文字種別を送信する

③ Lambda関数が既存レコードの絵文字種別を更新する

### リアクション取消

① ユーザーが自分のリアクションを再度タップして取り消す

② フロントエンドがAPI Gateway（`DELETE /reactions/{id}`）を呼び出す

③ Lambda関数がDynamoDBから対応するリアクションレコードを削除する

### 受け入れ条件
- 同一ユーザーが同じ投稿に複数のリアクションを付けた場合、変更として扱われる
- 取消後はリアクション集計に反映される
- リアクションの集計結果（絵文字ごとの件数）が投稿詳細に表示される

---

## 7. 同じリアクションをした利用者をグループ表示する処理の流れ

① ユーザーが投稿詳細画面でリアクション集計の絵文字アイコンをタップする

② フロントエンドがAPI Gateway（`GET /reactions?postId=xxx&emoji=yyy`）を呼び出す

③ Lambda関数がDynamoDBから該当投稿・該当絵文字のリアクションレコードを取得する

④ Lambda関数がリアクションしたユーザーのニックネームとアバターの一覧を返却する

⑤ フロントエンドが同じ絵文字をつけたユーザーをグループ表示する

### 受け入れ条件
- 同じ絵文字リアクションをしたユーザーのニックネーム・アバターが一覧表示される
- リアクションの変更・取消が即座に反映される

---

## 8. 施設側がイベントを登録する処理の流れ

① 施設担当者が施設側画面にアクセスする（APIキーによる簡易認証）

② 施設担当者がイベント登録フォームに情報を入力する
  - 入力項目: 情報提供元・施設名、イベント名、開催日、開始時間、終了時間、対象年齢区分、開催場所、イベントの説明、タグ、公式サイトURL、イベント画像（任意、1枚まで）

③ 施設担当者がイベント画像を選択した場合:
  - フロントエンドがAPI Gateway（`POST /events/upload-url`）を呼び出し、署名付きURLを取得する
  - フロントエンドが署名付きURLを使用してS3バケット（`sanji-demo-images`）に画像を直接アップロードする

④ フロントエンドがAPI Gateway（`POST /events`）にリクエストを送信する（HTTPヘッダーにAPIキーを付与）
  - 画像がアップロードされた場合、S3上の画像パスをリクエストボディに含める

⑤ API GatewayがAPIキーを検証し、有効であればLambda関数を呼び出す

⑥ Lambda関数がULIDでイベントIDを生成し、開催状態を「開催予定」に設定してDynamoDBのイベントテーブルに保存する
  - 画像がある場合はimageUrl属性にS3の画像パスを保存する

⑦ 登録完了のレスポンスを返す

### 受け入れ条件
- APIキーが無効な場合、403エラーが返される
- イベントIDはULIDで自動生成される
- 初期の開催状態は「開催予定」
- 登録日時・更新日時が自動で付与される
- 画像は任意（未設定でもイベント登録可能）
- 1イベントにつき画像1枚まで
- 対応フォーマット: JPEG, PNG
- ファイルサイズ上限: 5MB
- 画像はS3バケット（`sanji-demo-images`）に保存され、DynamoDBにはURLのみ保存される

---

## 9. 施設側がイベントの開催状態を変更する処理の流れ

① 施設担当者がイベント管理画面で対象イベントを選択する

② 施設担当者が開催状態を変更する（5種類から選択）
  - 開催予定 / 中止 / 延期 / 受付終了 / 開催終了

③ フロントエンドがAPI Gateway（`PATCH /events/{id}/status`）にリクエストを送信する

④ Lambda関数がDynamoDBのイベントレコードの開催状態と更新日時を更新する

⑤ イベントレコードは削除されず、状態が更新されて保持される

### 受け入れ条件
- 開催状態は5種類:「開催予定」「中止」「延期」「受付終了」「開催終了」
- 中止・延期になったイベントも削除しない（状態更新のみ）
- 更新日時が自動的に現在時刻に更新される
- 施設側APIのみAPIキー必須（一般ユーザーの閲覧は制限なし）

---

## 10. 「行ってみたい」を保存・表示する処理の流れ

### 保存

① ユーザーがイベント詳細画面で「行ってみたい」ボタンを押す

② フロントエンドがイベントIDをブラウザのLocalStorageに保存する（サーバー通信なし）

③ ボタンの表示が「保存済み」に切り替わる

### 一覧表示

① ユーザーが「行ってみたい」一覧画面を開く

② フロントエンドがLocalStorageからイベントIDリストを取得する

③ フロントエンドがAPI Gateway（`GET /events?ids=xxx,yyy`）で対応するイベント情報を取得する

④ 各イベントの最新の開催状態を含めて一覧表示する

### 受け入れ条件
- 「行ってみたい」はLocalStorageに保存（サーバーへの送信なし）
- 開催状態が変わっても一覧から削除されない（最新の状態を表示する）
- プロフィール（ニックネーム・子どもの年齢区分・アバター）もLocalStorageに保存する
- ブラウザのデータを消去するまで保持される

## 11. サーバーレス構成といえる理由

| 観点 | 説明 |
|------|------|
| サーバー管理不要 | EC2等のサーバーを一切使わない。全てAWSのマネージドサービス |
| 従量課金 | リクエストが0件なら課金も0円。待機コストが発生しない |
| 自動スケーリング | アクセスが増えてもAWSが自動で処理能力を調整する |
| コンピューティング | Lambda（呼ばれたときだけ起動する関数） |
| データベース | DynamoDB（フルマネージド、サーバー管理不要） |
| ファイル配信 | Amplify Hosting（git push自動デプロイ、Webサーバー構築不要） |
| API層 | API Gateway（HTTPサーバー構築不要） |
| ファイルストレージ | S3（イベント画像の保存、サーバー管理不要） |

---

## 12. 料金を抑えるために必要な設定

| 設定項目 | 内容 | 理由 |
|---------|------|------|
| DynamoDBのキャパシティモード | オンデマンド | 読み書きが発生しないときは課金ゼロ |
| Lambdaのメモリ割り当て | 128〜256MB | メモリが多いほど料金が高い。デモには最小限で十分 |
| Lambdaのタイムアウト | 10秒以内 | 意図しない長時間実行を防ぐ |
| Amplify Hosting | 無料枠を活用 | 月間1,000ビルド分・15GB配信・5GBストレージが無料 |
| API Gatewayのタイプ | HTTP API（REST APIではない） | HTTP APIはREST APIの約70%安い |
| CloudWatch Logsの保持期間 | 7日間 | ログ蓄積によるストレージコストを抑える |
| S3のバケットポリシー | パブリックアクセスブロック | 不要な外部アクセスを遮断（セキュリティ兼コスト） |

## 13. 使用しない方がよいAWSサービスと理由

| サービス | 不使用の理由 |
|---------|-------------|
| Amazon EC2 | 常時稼働サーバー。停止忘れで課金が継続するリスクがある |
| Amazon RDS / Aurora | 常時稼働のリレーショナルDB。DynamoDBで十分対応可能 |
| Amazon Cognito | 本格的なユーザー認証サービス。デモには過剰で実装が複雑 |
| Amazon ECS / EKS | コンテナオーケストレーション。デモ規模には過剰 |
| AWS WAF | Webアプリケーションファイアウォール。デモには不要で追加費用が発生 |
| Amazon ElastiCache | インメモリキャッシュ。デモのアクセス量ではDynamoDB直接で十分 |
| Route 53（独自ドメイン） | ドメイン登録に年間費用が発生。Amplify Hostingデフォルトドメインで十分 |
| Amazon SES | メール送信サービス。メール通知機能は実装しないため不要 |

## 14. 発表用デモで想定されるおおよその費用

### 前提条件
- デモ期間: 1〜2週間
- 想定アクセス: 発表当日に20〜50人程度が同時アクセス
- データ量: 投稿100件、リアクション200件、イベント30件程度

### 費用見積もり

| サービス | 月額費用目安 | 備考 |
|---------|-------------|------|
| AWS Amplify Hosting | 0 USD | 無料枠：月間1,000ビルド分、15GBデータ配信、5GBストレージ |
| Amazon API Gateway | 0 USD | 無料利用枠：月間100万リクエスト（HTTP API） |
| AWS Lambda | 0 USD | 無料利用枠：月間100万リクエスト、40万GB秒 |
| Amazon DynamoDB | 0 USD | 無料利用枠：25GB、月間25WCU/25RCU |
| Amazon S3（画像保存） | 0 USD | 無料利用枠内（5GBストレージ、20,000 GETリクエスト）。画像30枚×5MB＝150MB程度で十分収まる |
| CloudWatch Logs | 0〜0.1 USD | 少量のログ出力のみ |
| **合計** | **0〜1 USD** | ほぼ全て無料利用枠内に収まる見込み |

※ AWSアカウント作成から12ヶ月以内であれば無料利用枠が適用される

## 15. デモ終了後に停止または削除すべきAWSリソース

### 削除対象リソース一覧

| 優先度 | リソース | 削除理由 |
|--------|---------|---------|
| 高 | Amplifyアプリ | フロントエンドの配信を停止し、関連リソースを一括削除 |
| 高 | API Gateway | APIエンドポイントを閉じる |
| 高 | Lambda関数 | 不要な関数呼び出しを防ぐ |
| 中 | DynamoDBテーブル | データが不要になったら削除（必要なら事前にエクスポート） |
| 中 | S3バケット（sanji-demo-images） | 画像ファイル削除→バケット削除の順 |
| 中 | CloudWatch Logsロググループ | ログ保存料金の防止 |
| 低 | IAMロール・ポリシー | 費用は発生しないが不要なら削除して整理 |

### 削除方法

- **推奨**: AWSマネジメントコンソールまたはAWS CLIから削除
- **Amplifyアプリ**: コンソールからアプリを削除するだけでフロントエンド関連リソースが一括削除される
- **識別**: バックエンドリソース名にプレフィックス `sanji-demo-` を付けて削除対象を明確化

## 16. AWS初心者が実装する場合の推奨実装順序

| 順番 | 作業内容 | 完了の確認方法 |
|------|---------|---------------|
| 1 | DynamoDBテーブルの作成 | コンソールでテーブルが表示される |
| 2 | S3バケット（sanji-demo-images）の作成 | コンソールでバケットが表示される |
| 3 | Lambda関数の実装とデプロイ | テストイベントで関数が実行できる |
| 4 | API Gatewayの設定とLambda統合 | curlやブラウザでAPIが呼べる |
| 5 | Amplifyアプリの作成とGitHubリポジトリ接続 | git pushでビルドが自動実行される |
| 6 | CORS設定とAPI接続テスト | フロントエンドからAPIが呼べる |
| 7 | 施設側アクセス制限の設定（APIキー） | APIキーなしのリクエストが拒否される |

### 推奨事項
- 各ステップの完了後に動作確認テストを行うこと
- AWSマネジメントコンソールで手動設定する
- AmplifyはGitHubリポジトリのmainブランチと接続し、pushのたびに自動デプロイされることを確認する

## 17. セキュリティ上、最低限必要な対策

| 対策 | 内容 | 対象 |
|------|------|------|
| HTTPS通信 | 全通信をHTTPS経由にする | Amplify Hosting（自動対応） |
| S3アクセスブロック | パブリックアクセスをブロックし、署名付きURL経由のみ許可 | S3バケット（画像保存用） |
| CORS制限 | 許可オリジンをAmplifyドメインのみに限定 | API Gateway |
| 最小権限IAM | Lambda関数に必要最小限のDynamoDB・S3アクセス権限のみ付与 | IAMロール |
| 入力バリデーション | Lambda関数で入力値を検証し、不正リクエストを拒否 | Lambda |
| APIキー管理 | 施設側APIにAPIキーを必須とし、不正登録を防止 | API Gateway |
| シークレット管理 | AWSアクセスキーをソースコード・リポジトリにコミットしない | 開発プロセス |
| 環境変数管理 | APIキーはフロントエンドの環境変数で管理（ビルド時に埋め込み） | フロントエンド |
| 画像アップロード制限 | ファイルサイズ上限5MB、JPEG/PNGのみ許可 | Lambda（署名付きURL生成時にContent-Type・サイズを制限） |

## 18. 発表用デモとして省略できる運用機能

| 省略する機能 | 本番環境で必要な理由 | デモで省略できる理由 |

## 3案の比較と推奨

### 比較表

| 比較項目 | 案A: 最も安い構成 | 案B: 最も簡単な構成 | 案C: バランス構成 |
|---------|------------------|-------------------|------------------|
| **使用サービス** | S3（静的ホスティング）+ API Gateway + Lambda + DynamoDB | Amplify Hosting + API Gateway + Lambda + DynamoDB | S3 + CloudFront + API Gateway + Lambda + DynamoDB |
| **CDN/配信** | S3の静的ウェブホスティング（HTTPのみ） | Amplify内蔵CDN（HTTPS対応） | CloudFront（HTTPS対応） |
| **HTTPS対応** | ✕（HTTPのみ） | ○ | ○ |
| **実装難易度** | 低 | 最も低い（git push自動デプロイ） | 中（各サービス個別設定） |
| **月額費用目安** | 0〜1 USD | 0〜1 USD | 0〜2 USD |
| **初心者向け** | ○ | ◎（最も簡単） | ○（学習価値が高い） |
| **デモ機能充足** | △（HTTPS非対応で一部機能制限あり） | ○（全機能対応） | ○（全機能対応） |
| **セキュリティ** | △（通信暗号化なし） | ○（Amplifyデフォルト設定） | ○（OAC・CORS設定要） |
| **削除しやすさ** | 容易 | 最も容易（Amplifyアプリ削除で一括） | 容易（リソース名のプレフィックスで識別して個別削除） |
| **AWS学習効果** | 中 | 低（Amplifyが抽象化） | 高（各サービスを個別に理解） |

### 推奨: 案B（Amplify Hosting + API Gateway + Lambda + DynamoDB）

以下の理由から案Bを推奨する：

1. **セットアップが最も簡単**: Amplify Hostingを使えば、GitHubリポジトリを接続するだけでフロントエンドのビルド・デプロイが自動化される
2. **git pushで自動デプロイ**: コードを更新してpushするだけで本番反映される。手動でS3にアップロードしたりCloudFrontのキャッシュを無効化する必要がない
3. **初心者2人でも管理しやすい**: CloudFrontやS3の設定（OAC、バケットポリシー等）を個別に行う必要がなく、ミスが起きにくい
4. **HTTPS対応が自動**: SSL証明書の発行・更新をAmplifyが自動で行うため、設定作業ゼロ
5. **Amplifyアプリ削除で一括クリーンアップ**: デモ終了後、Amplifyアプリを削除するだけでフロントエンド関連リソースをまとめて削除できる
6. **費用が安い**: Amplifyの無料枠（月間1,000ビルド分、15GB配信）で十分収まるため、案Cと同等以下のコスト
